# 検証方針

確認日は2026年10月29日です。
知識DBの運用が成立すれば、コードと再現用の架空データをOSSとして公開することを目標にします。
今回承認された作業は検証への着手です。D1の採用、本番への正本移行、GitHubでの公開は今後の判断です。

## 設計仮説

知識を、質問単位の調査結果、原資料と版、採用済みの決定に分ける案を検討します。
結論の条件・根拠・確認日を保持し、採用状態と情報の検証状態を区別します。
タスク管理は既存の作業システムに残し、知識の確定版を参照します。

通常の取得はコードで検索・絞り込み・組み立てを行い、毎回の追加LLM要約を前提にしません。
質問単位で保存する価値と、原資料の節をそのまま取得する価値を比較します。
短い原文まで必ず要約することは要件にしません。

## 第一段階の範囲

第一段階のCは、節をSQLiteで管理する小さな比較器です。
質問単位の記憶生成、全文の意味理解、LLMによる回答、MCP公開、D1デプロイは含みません。
ここでD1や最終データモデルの採用を決めることはできません。

| 仮説 | 第一段階で扱う範囲 | 追加で必要な測定 |
| --- | --- | --- |
| 現状に十分な削減余地がある | 文書の返却量を再生して比較 | 実際のクライアントusageと再読込 |
| 少ない文脈でも根拠が揃う | 指定引用の取得、例外・複数資料 | 回答品質と後続作業の完了 |
| DB管理に追加価値がある | 同じ候補集合で状態フィルターを比較 | 質問単位の記録と更新工数 |
| 更新費用を含めて利益が残る | 前処理とローカル処理を記録 | 抽出・再索引・人の修正・請求 |
| 複数botと障害に耐えられる | 競合・再送・ロールバック・復元 | 認証・ネットワーク・D1・連携失敗 |

## 数値の判断

取得トークンを約3分の1にすることを探索目標に置きます。
達成しても、品質や運用費用を確認するまで全体の効率改善とは扱いません。
少量の文脈で根拠を落とす場合は、予算・分割・追加取得の設計を見直します。
総費用は、失敗と再試行を含む期間内の費用を、品質基準を満たした成功件数で割ります。
トークン数、金額、経過時間、人の修正時間を混ぜて一つの倍率にはしません。
