# 共有Hub：全文と差分を16体で比較

## 結論

Notionを正本にしたまま、各botの受領版からの差分と全文を同じ受領IDで比較し、トークン数が少ない方を配信する。自作の合成8ページ×16体で全128配信が小さい方を選び、本文を正確に復元・保存して受領した。全文84件（未読40・既読44）、差分44件。初読・復旧には全文、同数なら既読は差分を使う。

各ページとも旧版5体、中間版6体、未読5体。開発用の2ページは除外した。配信量は3方式で同じコンパクトJSON（ページID・受領ID・ハッシュ込み）を `o200k_base` で計数。自動方式を実際にHTTP配信し、対照の全文・差分は同じIDで作り、どちらの復元も確認した。ツール応答は同じ配信をbot実装とMCP SDKに通し、生成されたテキストを数えた。初回取得やツール応答を最終配信量と合算しない。

## 失敗例

短文や全面改稿では差分の管理情報が節約分を超えた。従来方式で実Notionの短文にかかっていた80トークンの超過は、自動選択で解消した。一方、192行の中央1行のみの変更は差分が有利で、従来方式と自動選択がともに22,947（全文66,393）。形式を変えただけの「更新」通知を防ぐため、botは保存した本文を比較する。

## 再現方法

Python 3.11以上。新しい出力先を指定する。Notion資格情報・モデルAPIは不要。初回のみトークナイザー辞書を取得する。

```sh
python -m pip install -e '.[hub]'
export TIKTOKEN_CACHE_DIR="$PWD/tokenizer-cache"
python scripts/measure_hub_auto.py --out runs/phase2-hub-auto-reproduction-001
python scripts/measure_hub_tool_text.py runs/phase2-hub-auto-reproduction-001 runs/phase2-hub-auto-reproduction-001/tool-text.json
```

受領IDは実行ごとに発行するので再実行時の合計は若干変動する。各実行内では同じIDを3方式に使い、全件で選択・復元を検証する。本文を生成する[評価条件](../fixtures/phase2-hub-auto-v1/cases.json)と、展開した全文のハッシュを照合する。短文の実Notion試験は非公開の履歴を使用し、ここには集計だけを収録した。

## 未検証事項

16個のクライアント状態を1台で動かした制御試験。実業務の頻度、外部ホスト間の通信時間、サーバーのCPU増分、実モデルの課金・回答品質は測っていない。

## 次の判断

この選択を共有Hubの標準とする。業務全体の効果を判断するには、個別本文を記録せず、初読・再読と編集の頻度を測る。
