# 知識取得方式の検証プロトコル

## 検証する判断

目的は、調査や引き継ぎを同じ品質で完了するための総費用を減らせるか確かめることです。資料の保存先だけでなく、保存単位、取得方法、更新方法を含む運用方式を比較します。DBへの移行や、特定の削減倍率を先に結論にしません。

最初の試験では、原文の根拠を自動で取得する処理を実装して測定します。取得内容から最終回答を生成するモデルや、実際のbotの作業完了までは、この試験だけでは評価できません。

## A・B・Cの比較

| 方式 | 内容 | この段階で分かること |
| --- | --- | --- |
| A | 共通の文書ランキングで選んだ候補文書を全文返す | ローカルに保存した全文取得方式の比較基準 |
| B | 候補文書の原文の節を選んで返す | 取得する範囲を絞る効果 |
| C | SQLiteに保存した節と明示的な状態・期間などで取得する | 構造化した記録とフィルターを使う追加効果 |

Aは現在のNotion運用全体を再現するものではありません。認証、通信、Notion検索、モデルによるツール選択と追加検索を含まない、ローカルの再生基準です。実際のNotion応答を使う場合も、取得済み応答の再生と、オンラインで新たに取得した処理を区別します。

CはローカルSQLiteでの試験です。Cloudflare D1への往復時間、課金、同時実行、複製、復旧は未検証です。BとCで保存単位や候補選定も変わる場合、差をDBという保存媒体だけの効果とは解釈しません。

質問、原資料、公開範囲、担当bot、基準日、質問のmodeは、各方式に同じ条件で渡します。文書候補の上限、順位付け、返却予算、原文への追加アクセス条件は実行記録に残します。全文を返すAと、取得予算を設けるB・Cの差は実験条件として明記します。

## 評価データ

公開を想定した架空データと、本人の実資料を使う非公開データを分けます。公開データへ実資料を複写したり、実際の氏名・URLを置き換えただけの資料を混ぜたりしません。公開用fixtureの成績を、本人の作業での改善率とは扱いません。

現在の架空データは18文書、61節、30問です。調整用10問と評価用20問に分けていますが、同じ開発チームが設計した開発用fixtureです。独立したholdoutや第三者によるベンチマークとは呼びません。実装担当が評価結果を使って調整した場合は、その事実と対象問題を記録します。

実資料の評価では、質問と必要な根拠を取得方式の結果を見る前に固定します。方式の調整に使う資料や質問を分け、短い資料、再利用の少ない資料、複数資料、旧版、未採用案、回答に必要な情報がない場合も含めます。日常作業の改善倍率を求めるときは、評価問題の分類ごとの出題数ではなく、実際の利用割合を使います。

## 測定する項目

| 項目 | 定義と限界 |
| --- | --- |
| 必須引用の取得率 | 必要な原文のうち返却コンテクストに含まれた割合。最終回答の正答率ではない |
| 必須引用をすべて取得した件数 | 回答可能な質問のうち、指定された引用がすべて含まれた件数。引用同士の関係をモデルが理解したかは未評価 |
| 参照範囲の違反 | 許可されていない個別記録の内容が返却された件数。権限外の識別語で確認する |
| 返却量 | モデルへ渡すpayload全体の文字数またはトークン数。本文だけでなく、出典や警告なども含める |
| 取得時間 | ローカルの取得処理が完了するまでの時間。ネットワークや回答生成の待ち時間を含まない |
| 準備・更新費 | 初回の取り込み、索引作成、変更部分の更新に要した時間や追加処理 |
| 取りこぼし | 予算不足、候補外、順位の低さ、期間フィルターなどの理由。返却なしを情報不存在と扱わない |

返却量は、使った計数方法と単位を結果に付けます。Unicode文字数をトークン数と呼びません。参照用encoderを使ったトークン数は、そのencoderに対する実測値です。実運用のGrokなどのトークン数や課金額と同一とは扱いません。モデルが報告する利用量を取得できた段階で、入力、出力、キャッシュの扱いを含む実利用量を別に測定します。

初回の索引作成時間と各問い合わせの時間を分けます。同じ知識が更新されるまでに何回使われたかを測り、取り込み・更新費用を配分します。取得1回だけを見て、運用全体の費用が同じ倍率で下がったとは報告しません。

## 品質の判断

通常の事実、条件と例外、複数資料の組み合わせ、時間、決定変更、情報不足、引き継ぎを評価対象にします。LongMemEvalは情報抽出、複数の記録をまたぐ推論、時間、知識の更新、回答保留を分けて評価しています。MemoryArenaは、過去の情報を思い出せることと、後続の作業で利用できることの差を扱っています。

この試験で根拠を正しく取得できた場合も、最終回答の品質やbot間の引き継ぎが成立したと結論にしません。次の段階では、同じモデルと同じ評価条件で回答を生成し、必要な条件の欠落、提案と採用の混同、根拠の取り違え、情報不足への対応を確認します。引き継ぎは後続作業が完了したかで評価します。

旧決定をコンテクストに含めたことだけで誤答としません。履歴を説明する質問では旧版が必要です。一方、現在の決定を問う質問で旧版だけを返した場合は、根拠不足として記録します。質問のmodeを人が指定した試験は、自然言語からmodeを自動で判断する能力の評価とは分けます。

回答可能でない質問を、検索結果が空だっただけで正答にしません。取得できなかった理由が、情報不足、検索器の失敗、権限の不足のどれかは別に確認します。

## 件数増加と複数bot

資料件数を増やす試験では、無関係な文章だけでなく、似た調査、異なる条件、旧版を加えます。返却上限を固定するだけでは、根拠を落としていても返却量が一定になります。返却量、根拠の取得率、追加取得回数、所要時間を一緒に見ます。生成した大量データによる負荷試験と、実資料での検索品質は別に報告します。

複数botの試験では、同時更新、同じ要求の再送、保存済みなのに応答だけが失われた場合、保存直後の参照、参照範囲を確認します。taskflowとの連携では、根拠の保存が確定する前に完了扱いにならないことを確認します。ローカルの整合性試験に合格しても、本番環境での同時実行や可用性の保証にはなりません。

可用性の評価は、障害時に参照できる範囲、情報の時点、保留すべき処理、復旧手順と実測復旧時間を対象にします。短期間に停止しなかったことから年間の稼働率を保証しません。

## 結果の報告と採用判断

各実行には、コードの版、コーパスと質問のハッシュ、実行設定、計数方法、実行環境、日時を残します。方式ごとの平均だけでなく、分類ごとの結果と失敗例を併記します。小規模な試験で重大ミスがゼロでも、一般的な品質維持の証明とはしません。

取得トークンを現状の3分の1程度にする案は探索目標です。達成を前提にしたり、3倍に届かなければ価値がないと決めたりしません。品質を保った完了1件当たりの総費用と、更新・保守の負担を比較して採用範囲を決めます。トークン数、金額、完了時間、保守時間はそれぞれの単位で報告します。

現段階で実測できるのは取得処理です。最終回答、作業完了、実クライアントの利用量、D1の本番挙動を測っていない結果から、全体が1.6〜1.9倍効率化したとは主張しません。
