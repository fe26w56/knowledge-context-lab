# 次段階の提案：16体の仕事全体で、再利用の利益を測る

## 推奨する方向

次の本命は、16体に共通する調査・根拠整理を再利用し、更新時に必要な部分を作り直し、根拠が足りなければ原文へ戻れる方式の検証である。保存先は当面ファイルを維持する。

大きな利益が出る条件は、同じ根拠や調査結果を複数回使うこと、再利用する情報が適用条件を保つこと、生成・確認・更新の費用を回収できること。この条件は現在の単発質問の比較からは分からない。共有が少ない案件や頻繁に更新される案件を含め、利益が出ない条件も測る。

目的は同じ品質で費用と時間を下げること。DB、要約、共有記憶、ベクトル検索のどれを導入するかを先に結論にしない。実資料の持ち込み・公開・本番移行は禁止された範囲のままとする。

## 候補と、採用しない条件

| 順序 | 候補 | 利益があり得る理由 | 負担・不採用条件 |
| --- | --- | --- | --- |
| 1 | 同一条件の検索・調査要求のまとめ実行と再利用 | 同じ要求を同時に何度も処理する無駄を減らす。最初は生成内容を変えない比較にできる | ローカル検索だけの再利用では、モデルが読むtokenや回答生成は減らない。重複が少なければ利益が小さい |
| 2 | 根拠・版・条件付きの共有記録 | 一度作った根拠整理を後続の複数タスクが利用し、同じ整理を作り直す処理を減らす | 作成・検査・更新の費用が増える。誤りを全員へ伝える危険もある。短文・低再利用では全文より高くなり得る |
| 3 | 必要な場合だけ原文を追加取得 | 共通記録で十分なタスクは軽く、条件や例外を確かめるタスクは原文まで読む | 不足の見逃しや余分な往復が起きる。品質を戻しても総費用やp95が悪化すれば採用しない |
| 条件付き | 語句検索＋意味検索、候補の再順位付け | 言い換えや別名で正しい出典が候補に入らない失敗に対応する | 索引作成・更新・追加モデルの費用を伴う。根拠が既にあるのに読み違える失敗には直接効かない |
| 後段 | SQLite / D1 / 分散サービス | 更新競合や共通snapshotの要求がファイルの運用で満たせなくなった場合に検討する | 保存先の変更だけをモデル品質・費用の改善と扱わない。D1はそのサービスでの実測が必要 |

質問単位の記憶は当初の設計仮説への復帰であるが、自動的に正しい決定や確定知識にはしない。生成した主張と、原文の引用、採用状態、検証状態を分けて保存する。[当初の方針](decisions.md)

## 共有記録の最小要件

一つの記録には、対象となる問い・条件、主張、例外、未確定事項、原文引用、source IDと版、確認日・有効期間、共有範囲、生成方法の版を持たせる。短い原資料はそのまま残す案も比較する。出典や原文を閲覧可能にするだけでなく、そのタスクで使うときに権限を確認する。

再利用の単位は、質問が似ていることだけで決めない。actorの権限、scope、mode、as_of、参照可能なsnapshot、検索・生成設定が適合する必要がある。privateな結果はactorをまたいで共有しない。共有可能な原資料だけから作った記録で、安全に再利用できる範囲を先に確かめる。

初期版の失効は、関連資料のhashだけでなく可視コーパスの版も含めて保守的に行う。新しい決定が追加された場合、以前に参照した文書が一文字も変わらなくても記録が古くなるためである。権限変更・削除・状態変更も失効条件とする。TTLだけを最新性の保証にしない。

変更箇所だけの失効・再計算は、その安全な初期版から別の一変更として比較する。独立レビューが必要なタスクでは、他者の結論を使い回してレビューそのものを省略しない。共有で独立性を失うことを「効率化」と数えない。

## まず作る評価：案件が進むエピソード

架空の一つの案件について、調査 → 条件付きの決定 → 別actorへの引き継ぎ → 原資料の更新・決定の撤回 → 再質問、までを一組にする。actorごとに実際に別の文脈を使い、依存関係がある作業を無理に同時実行しない。

次の条件を開発用・最終用の両方に含める。共有が有利な案件だけを作らない。

- 短文と長文、似た文書と別条件の文書、複数出典が必要な決定。
- 再利用がない・少ない・多い案件。16体の中で問いが違う場合も含む。
- 更新なし、参照元の更新、新規文書による上書き、撤回、公開範囲の変更。
- 根拠不足、矛盾、否定条件、必要な根拠はあるが読解を誤りやすい案件。
- 共有側の誤った記録が後続タスクへ伝わる場合と、原文の追加取得で回復できる場合。

資料と問題の意味監査を先に行い、改善実装の前に開発・最終データと採点規則をハッシュ固定する。過去の最終問題は回帰用にする。問題ID、正解、要求出典のリスト、rubricを検索器・記録生成器・回答モデルに渡さない。自作の新しい案件も独立した外部ベンチマークとは呼ばない。

評価作者・実装者・採点者の役割を分け、同じ自動採点者の判断だけで確定しない。独立した人手採点がない間は、その限界を明記する。外部データは由来・ライセンス・実資料禁止との整合を調べてから別判断とし、現時点では取り込まない。

## 比較の順序

1. **基準と計測。** 6候補全文と12候補全文を、同じ案件・モデル・出力要件・権限・更新時刻で実行する。検索漏れ、供給済み根拠の読解失敗、古い記録の使用、重複生成の負担を分ける。品質の低い基準だけを選んで改善を大きく見せない。
2. **同じ内容の再利用。** 基準から、同一要求のまとめ実行・再利用だけを変える。出力内容が同じ場合、費用・時間のどこが減るかを確認する。
3. **共有記録。** 再利用版から、原文を根拠とする共有記録の生成・読み出しだけを変える。事前生成費用を隠さず、最初の利用から回収できるまでを測る。
4. **原文への追加取得。** 共有記録版に、不足時の原文取得だけを追加する。取得回数・停止規則は開発側で決める。不足判定の見逃しと過剰判定も測る。過去のAdaptiveRetrievalは別方式であり、その測定を新方式の証拠には流用しない。
5. **原因が残った場合の別実験。** 出典の検索漏れが主なら検索を改善し、根拠が揃っても読み違えるなら読み方・出力契約を比較する。モデル変更を試す場合も別の比較に分け、記憶方式の効果と混ぜない。
6. **最終評価。** 開発で構成・採点規則・費用計算・標本数を固定し、有望な方式と強い基準だけを未使用の案件で比較する。結果を見て検索器や閾値を変更しない。

## 成功の判定と費用

主指標は、必要品質を満たして完了した案件数、そのために使った総費用、案件の開始から引き継ぎ完了までの壁時計時間とする。token数、API usageによる費用推定、請求、訂正回数、人の訂正時間を別々に記録する。人が実際に直していない場合、人の作業時間を作らない。

共有方式の費用には、最初の記録生成・検査、読み出し、各actorの入力と出力、再試行、更新時の失効・再生成を含める。前処理費用を何回の再利用で回収できるかを表示する。同じ記録を16回モデルに渡せば、16回分の入力処理が自動的に無料になるわけではない。

アプリ側の再利用とproviderのprompt cacheは別々に計測する。新しい実行では入力・cached input・cache writeの内訳・出力・追加推論・失敗分を可能な限り保存し、実行時に確認した価格のsnapshotで計算する。旧名目費用の算式を無条件で流用しない。

「大きな改善」の探索目標案は、**同品質を維持して案件当たり総費用50%減、所要時間30%減**。これは期待値や測定済みの効果ではなく、狙う価値の目安である。品質を犠牲にして達成した値は不採用。費用と時間の一方しか改善しない場合は交換条件として報告する。

品質は案件全体の成功、必要条件・出典の保持、状態・権限・更新の扱いを確認する。重大な状態誤用や漏洩が観測された方式は採用しない。「差が有意でない」だけで同品質とはしない。案件単位の対応付き比較と不確実性を報告し、同品質の判断に必要な標本数・許容差は最終評価の前に固定する。16 actorや反復を独立した16案件として数えない。予算内で精度が足りなければ追加検証が必要とする。

既存の承認は合計10 USD。新規課金の前に現在の共通ledgerを再確認し、残額内で試行を予約する。保存済み会計の2.517592625 USDはcredit残高ではない。新しい上限や本番サービスを黙って追加しない。

## 研究を踏まえた位置付け

- MemoryArenaは、記憶が後続の行動に使われる相互依存タスクを評価する。外部記憶の有効性が課題に依存する結果から、単発質問に加えて案件全体を測る必要性を支持すると考える。このプロジェクトで共有記録が有効と実証した資料ではない。[MemoryArena](https://arxiv.org/html/2602.16313v2)
- LongMemEvalは情報抽出、複数記録、時間、更新、情報不足を区別する。次の採点でも最新性と不明時の扱いを残す理由になる。検索で根拠を渡すことと、その根拠を正しく使うことも分ける。[LongMemEval](https://arxiv.org/html/2410.10813v2)
- 共有記憶の権限・更新・削除の扱いは想起精度とは別の検証軸である。GateMemの問題設定は、共有記録に対して失効と可視範囲の試験を追加する参考になる。[GateMem](https://arxiv.org/abs/2606.18829)
- 記憶方式の費用は内部の生成・更新処理に左右され、元が取れる時点も方式とモデルで変わるという研究がある。事前生成費用と損益分岐を含める設計の参考であり、ここでの改善率は推定しない。[Total Recall at What Cost?](https://arxiv.org/abs/2608.11879)
- Contextual Retrievalは文脈を付けた索引・語句検索・意味検索・再順位付けを扱う。出典の候補漏れが主因の場合の候補とする。公開された削減率を、このコーパスに転用しない。[Anthropic](https://www.anthropic.com/research/contextual-retrieval)
- OpenAIのprompt cacheは共通prefixの計算を再利用するが、回答は新しく生成する。cacheの保存・読み出し費用も含めた計測が必要である。[公式ガイド](https://developers.openai.com/api/docs/guides/prompt-caching)

次の実装候補は、上記の案件評価と共有記録・追加取得。大きな進歩とは、特定の方式に決め打ちすることではなく、**どの再利用率・文書長・更新頻度なら、品質を保って費用と時間が下がるかを説明できる状態**まで進むことである。
