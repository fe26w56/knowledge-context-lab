# Phase 2の測定契約と実装境界

## 凍結と選定

`fixtures/phase2/FREEZE.json`は改善実装前に作った40問と21文書のSHA256を記録する。開発20問と最終20問を分離した。問題担当と実装担当は分けたが同じ開発チームの自作診断で、元の18文書も再利用する。独立したベンチマークとは呼ばない。

選定順は必須引用全揃い問数最大、条件欠落最少、旧版のみ最少、トークン最少、段階と予算。禁止引用と実行エラーは0を条件にする。既知q22/q30を回帰ゲートに使い、設定と検索実装のhashを固定してから最終問題を実行した。最終結果を見た後の検索実装変更はない。

検索入力は`text, actor, scope, mode, as_of`だけ。問題IDや正解は評価器だけが持つ。定義意図の展開語は「用語・略語・定義・名称」で、正解のKBや文書IDを挿入しない。ただしq22の失敗を見て追加したヒューリスティックである。

## 取得と保存

| 比較 | 揃えるもの | 変わるもの |
| --- | --- | --- |
| A / B | 候補文書、データ、権限、段階の設定 | 全文か、予算内の節・部分節か |
| B / C | レコード、フィルター、ランキング、候補、分割、予算、JSON | ファイルかSQLite保存か |

両保存先は起動時に全レコードを読み、同じPython索引を作る。索引再利用時のquery中I/Oは0。CはSQL検索やFTS5の評価ではない。Aは全文の比較で予算を超え、文書内の履歴・提案をラベル付きで含み得る。

段階2は状態・有効期間を候補対象の選定前に判定する。currentはdecisionのadopted、historyは過去の有効区間を選ぶ。ただし文書ランキングの特徴には同じ文書内の別状態の節も含まれ、状態別索引ではない。mode/as_ofは呼び出し側が正しく与える必要がある。

表は列ヘッダーと全体注記を繰り返し、行を切らずに分割する。通常文は文単位。複数表の混在や離れた文の条件・例外を一般的に束ねる保証はない。原文spansにより抽出内容は追跡できるが、意味的な完全性は別途検証が要る。

## 指標

必須根拠全揃いは、answerableかつexpected_quotesを持つ問題で全引用が返却本文にあること。部分文字列照合であり、回答の正しさではない。情報不足を説明する根拠を求める問題も含む。expected_quotesがない問題に空結果の正答点を与えない。

condition_missingは指定条件引用の欠落。obsolete_onlyは旧引用があり必要引用が一つもない場合。旧引用と現引用の併存を誤答と扱う指標ではない。forbidden_quote_hitsは指定禁止文字列の検出で、完全な漏洩検査ではない。別に保存payloadのsource IDとactor/scopeも照合する。

全返却JSONの参照トークンを数える。20問合計は1回分で、未採点1問も含む。時間は繰り返し全試行の中央値・p95。query時間はランキング・選択・予算判定・JSON作成を含み、LLMやネットワークを含まない。各試行でtoken-countキャッシュをクリアし、辞書自体は事前ロードする。

最終評価のcold_indexは毎query保存先を再openし索引を構築、warm_indexは索引を再利用する。順序はシャッフルする。OSキャッシュは消去しない。規模試験はbackendごと3回の再構築後に7問を実行し、setupを各問へ加えた単一query想定値も保存する。7問の実測合計として足してはならない。同一ホストの変動を含み、プロセスやOSを隔離した冷起動試験ではない。

追加探索はローカル候補枠を3→6→12へ拡張する。特徴被覆0.75、増分なし、全候補到達、3roundまたは12候補で停止。全roundの時間を含む。HTTP追加取得ではない。選定候補は拡張なし1round、呼び出し1回、再試行0回。

## 規模試験

21文書を残し100 / 1,000 / 10,000へ増やす。生成比重は完全複製18、類似27、条件違い18、旧版15、相反案12、無関係10。実際の生成数と本文ハッシュ重複率はmetadataに保存する。重複率の分母は追加文書数。旧版・相反案にも同一本文が生じるため、完全複製カテゴリ比率とは異なる。

文字列引用到達率と、元fixtureのsource IDにも一致する到達率を分ける。後者は元の根拠を見失わないかの診断で、同等の複製文書を不正解にする場合もある。相反文章内の引用も前者に数えられるので、前者だけで品質を語れない。開発側の固定7問・seed1つで、大規模な意味的多様性を保証しない。

差分更新は1文書の書き換え・読み戻し・再索引の一致を確認する。commitと全再索引は別計時。1/16/1600queryあたりの償却値はローカルmsのシナリオで金銭費用ではない。並列16readerやキャッシュ無効化の性能は未測定。

## 更新と障害

FileAdapterは1文書atomic replacementで、複数文書transaction/CASを持たない。SQLiteAdapterは取得用JSONの一括transactionで、版比較やrequest_idを持たない。別のKnowledgeStoreがrevision/head/requestを一transactionで保存する。両者の自動同期はない。

16writerは独立接続。競合後は明示的に再読込し、全botのeventを保持するmergeを順次再適用する。自然文競合を自動解決した試験ではない。commit直後のACK喪失、SQL triggerによるtransaction途中失敗、private/shared、backup/restoreを試す。

復旧時間は小さいローカルDBの復元と全table/head/request再送確認まで。taskflowスタブは未確認ACK・異record/version・復元で消えたcommitを完了扱いにしない。実taskflow・HTTP・D1は未測定。

## 再現性と関連研究

fixtureのbyte SHA256、設定、検索3モジュールのimplementation hash、評価器hash、実行時ソースコピーを保存する。負荷・障害はsource_sha256も持つ。implementation hashだけで評価器の同一性を主張しない。旧データ・結果を変更せず新しい出力先を要求する。

索引・取得・回答を分離し、更新や回答保留も評価する設計は[LongMemEval論文](https://arxiv.org/abs/2410.10813)も参照した。本プロジェクトではそのベンチマークを実行しておらず、その数値を本実装の性能として使わない。
